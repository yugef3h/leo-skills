# 导言

现有 AI 代码生成工具以输出结果为单一导向，存在工程化思维缺失问题：缺乏存量组件复用意识、不具备逻辑分层与模块化拆解能力，同时忽略性能调优、行业编码规范与工程最佳实践，产出方案完整性、健壮性不足。因此需通过AGENTS.md智能代理配置、标准化规则集、底层约束边界、MCP 工具链等机制形成规范管控体系，补齐工程化短板。

# 核心结论：不用每次手动读、不浪费上下文，靠「静态持久规则 + 分片懒加载 + 条件注入」解决中小仓上下文膨胀问题
先区分两个概念：
1. `.cursorrules` / `.clinerules` 是**常驻底层约束**，不会挤占对话上下文，工具在后台读取，不占token；
2. `component-registry.md` 全量塞进对话才会浪费token，中小仓不能全量喂，要做分片按需加载。

## 一、先讲清楚：为什么规则文件不耗上下文
Cursor/Cline/Copilot 这类Vibe工具的机制：
- 规则文件属于**项目全局系统提示词（System Prompt）**，工具启动时一次性加载进模型底层配置；
- 不会追加到你每一轮用户聊天消息里，对话上下文窗口看不到这部分内容；
- 只做行为约束：“优先复用组件、禁止自建表格”，不携带大量组件示例代码，文本极短，token损耗可忽略。

痛点只出在**组件清单文档**：几百行组件示例全量丢进对话，每轮交互都重复携带，上下文瞬间被占满、推理变慢、容易截断。

## 二、中小单仓库轻量化方案（无中台、无MCP，零额外服务，解决清单上下文膨胀）
### 方案1：组件清单拆分 + 按需引用（最推荐，零成本）
把一份大 `component-registry.md` 拆成三类文件，避免一次性全载入：
1. `components/COMMON.md`：通用基础组件（Button、Input、Modal），体积小，可全局常驻；
2. `components/BIZ_LIST.md`：列表类组件（BizTable、SearchFilter）；
3. `components/BIZ_FORM.md`：表单类组件；
4. `components/SPECIAL.md`：小众特殊业务组件。

#### 使用方式（按需引入，不加载无关内容）
写需求时只引入当前页面需要的组件分片，示例Prompt：
```
# 仅注入当前页面相关组件，不加载全部
@components/BIZ_LIST.md
@components/COMMON.md
需求：生成客户管理列表页面
约束遵循.cursorrules，仅使用上述文件内组件，不新增基础UI
```
优势：单次上下文只带20–50行组件示例，token占用极低，无关组件完全不参与对话。

### 方案2：工具内置文件检索指令，AI主动查询，不预加载
Cursor 支持 `read_file`、`search_code` 内置工具调用，不用你手动把文件塞prompt：
在 `.cursorrules` 写入固定逻辑：
```
生成任何页面/模块前，自动执行两步工具调用，不提前加载全部组件：
1. search_code "src/components/biz" 检索匹配当前场景的组件；
2. read_file 读取匹配到的组件tsx源码、props类型；
仅把检索命中的少量组件源码加入本次上下文，未命中组件不读取。
禁止一次性读取全部组件目录文件。
```
流程：
1. AI收到需求 → 后台检索组件目录；
2. 只拉取2–3个匹配度最高的组件代码进本轮上下文；
3. 匹配不到再询问是否扩展组件，不会加载全量清单。
完全规避“全量清单常驻对话”的上下文浪费，中小仓最优解。

### 方案3：区分「永久约束」和「临时素材」，隔离token消耗
1. 永久低token约束（`.cursorrules`）：只写行为禁令，无代码示例，常驻底层，不占对话上下文；
2. 临时高token素材（组件代码、示例）：**仅本次任务生效**，本轮对话结束自动丢弃，不会留存到下一次聊天；
工具底层天然隔离系统规则与对话上下文，不会叠加重复消耗。

## 三、进阶优化：缓存组件元信息，重复任务复用上下文
同一类页面（列表、表单）高频开发时，避免重复检索读取：
1. 第一次生成列表页：AI检索BizTable并加载源码；
2. 同会话内再写另一张列表：工具缓存已读取的组件类型，不再重复`read_file`，直接复用内存中的组件信息；
3. 新开会话才会重新检索，大幅减少重复文件读取带来的token损耗。

## 四、避坑：两种错误用法（会严重浪费上下文）
1. ❌ 把完整上千行组件清单粘贴到每一条prompt
   每轮对话重复携带，上下文窗口快速占满，模型遗忘需求、生成卡顿。
2. ❌ 规则文件里堆砌大量组件示例代码
   规则文件是系统prompt，过长会导致工具启动变慢、全局推理成本升高，规则只写约束，示例放到外部分片文件。

## 五、最简落地模板（直接复制，无上下文浪费）
### 1. .cursorrules（仅约束，无代码，token极少）
```
行为规则：
1. 开发页面前，自动调用search_code检索src/components/common、src/components/biz下匹配组件；
2. 仅read_file读取检索匹配到的组件，禁止读取全部组件文件；
3. 优先复用已有组件，现有组件不满足则输出扩展方案，禁止重新实现基础UI；
4. 统一使用@/components路径导入，严格遵守组件TS Props。
禁止：手动手写原生table/input/button，引入外部UI库。
```

### 2. 目录拆分，按需引用
```
src/
├── components/
│   ├── COMMON.md   # 小体积通用组件
│   ├── BIZ_TABLE.md
│   ├── BIZ_FORM.md
│   └── special/
```

### 3. 单次开发Prompt示例（轻量化）
```
@src/components/BIZ_TABLE.md
@src/components/COMMON.md
需求：商品库存列表页面，支持分页、状态筛选、批量操作
严格遵循.cursorrules复用组件，不自建表格筛选栏
```

## 六、对比大型MCP方案，中小仓这套方案的优势
1. 无额外服务、无需部署组件中台，仅靠文件分层+工具检索指令；
2. 上下文按需加载，单次仅携带少量组件代码，不会冗余；
3. 规则常驻底层，不用每次重复写约束话术；
4. 配合自定义ESLint做最终兜底，兼顾复用性与性能。

简单总结：只要不把全部组件清单全量塞进prompt，改用「AI自动检索+分片按需注入」，完全不会浪费上下文；全局规则文件本身不占用对话token，不存在重复读取损耗。
