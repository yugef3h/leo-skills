# Harness 支柱：质量保障工程

## 核心理念

**Harness = Guides（前馈标准）+ Sensors（反馈采集）→ 自动化验收。** Spec 定义了"做什么"，Harness 验证"做对了没"——不只是功能正确，还包括架构一致性、代码质量、规范遵循。

---

## 四大模块总览

```
Harness 质量保障
├── TDD（测试驱动开发）
│   └── Red → Green → Refactor 循环，受测试开关控制
├── Code Review（代码审查）
│   └── Spec 一致性 + 架构检查 + 代码质量
├── Refactor（重构）
│   └── 不改功能，优化架构和质量，人工引导 + AI 执行
└── AGENTS.md 维护
    └── 三次原则写入 + 大小监控 + 压缩 + 按需加载
```

---

## 模块 1：TDD（测试驱动开发）

### 测试开关机制

测试**默认关闭**（`test: false`）。

原因：AI 生成的测试用例问题越来越多，当前技术无法根治。盲目全量测试会导致：
- 测试本身有 bug，浪费调试时间
- 测试过于脆弱（brittle），改一行代码十个测试挂
- 测试维护成本超过收益

**开启场景（满足任一）：**
- 核心支付/计费逻辑
- 关键数据转换/计算逻辑
- 之前出现过回归 bug 的模块
- 第三方 API 集成的契约测试
- 人工明确要求开启

**开启方式：** 在 Implementation Spec 的 Task 级别声明 `test: true`：

```markdown
### Task 5: 价格计算逻辑
- test: true  ← 明确声明
- 原因：涉及金额计算，必须保护
```

### TDD 循环

```
┌──────────────────────────────────────┐
│  RED：写一条会失败的测试                │
│  - 只测试 spec 中定义的验收标准         │
│  - 测试必须能失败（不能是永远通过的）     │
│  - 一个测试只验证一件事                 │
└───────────────┬──────────────────────┘
                │ 测试失败 ✓
                ▼
┌──────────────────────────────────────┐
│  GREEN：写刚好让测试通过的最简代码       │
│  - 不写任何测试不需要的代码             │
│  - 不优化、不抽象、不提前设计            │
│  - 先让它工作，再让它优雅               │
└───────────────┬──────────────────────┘
                │ 测试通过 ✓
                ▼
┌──────────────────────────────────────┐
│  REFACTOR：不改功能，优化代码质量        │
│  - 消除重复                            │
│  - 改善命名                            │
│  - 提取函数/组件                       │
│  - 测试必须全程保持通过                  │
└───────────────┬──────────────────────┘
                │ 重构完成 ✓
                ▼
            下一个测试（循环）
```

### 测试分层（技术栈适配）

| 层级 | React 前端 (Testing Trophy) | Python/Go 后端 (Testing Pyramid) |
|------|---------------------------|----------------------------------|
| 顶层 | E2E (Playwright) — 极少，仅核心流程 | E2E — 极少 |
| 中层 | Integration (React Testing Library) — **重点** | Integration — 适量 |
| 底层 | Unit — 纯函数/工具函数 | Unit — **重点** |
| 基底 | Static Analysis (TypeScript/ESLint) | Static Analysis (mypy/golangci-lint) |

详细分层见 `references/testing-trophy.md`。

## 模块 2：Code Review（代码审查）

### 双重审查

每个 Task 完成后，AI 自动执行两轮审查：

#### 第一轮：Spec 一致性审查（必须通过）

审查代码是否忠实实现了 spec：

| 检查项 | 依据 |
|--------|------|
| 验收标准是否全部实现 | Requirements Spec 中的 AC-01, AC-02... |
| API 路由和数据结构是否匹配 | Design Spec 中的 API 设计和数据模型 |
| 组件边界是否被遵守 | Design Spec 中的组件职责表 |
| 业务逻辑是否正确 | Requirements Spec 中的业务规则 |
| 约束条件是否满足 | Requirements Spec 中的性能/安全/兼容性约束 |

**不通过处理：** 代码打回，在对应 Task 下新增子 Checklist，修复后重新审查。

#### 第二轮：架构与质量审查（建议通过）

| 检查项 | 内容 |
|--------|------|
| 架构合理性 | 代码结构是否符合 Design Spec 的分层设计？是否有跨层调用？ |
| 代码复用 | 是否有重复代码可提取？是否引入了不必要的抽象？ |
| 命名规范 | 文件、函数、变量命名是否清晰？是否遵循项目约定？ |
| 错误处理 | 异常是否被正确处理？错误信息是否有意义？ |
| 性能隐患 | N+1 查询、未记忆化的计算、不必要的 re-render |

### 审查输出格式

```markdown
## Code Review: Task #[N] - [Task 标题]

### Spec 一致性：✅ 通过 / ❌ 不通过

| AC 编号 | 验收标准 | 状态 | 证据 |
|---------|----------|------|------|
| AC-01 | [标准] | ✅/❌ | [代码位置或行为说明] |

### 架构与质量：建议

| 问题 | 严重程度 | 建议 | 文件:行号 |
|------|----------|------|-----------|
| [问题描述] | 🔴/🟡/🟢 | [改进建议] | `path:line` |

### 总结
- Spec 一致性：[通过/不通过，N 项待修复]
- 架构质量：[整体评价]
```

## 模块 3：Refactor（重构）

### 什么时候触发

- **定期触发**：每完成 5-10 个 Task 后，主动问用户是否需要重构
- **坏味道触发**：审查中发现以下信号——
  - 同一段逻辑在 3+ 处重复
  - 组件/函数超过 200 行
  - 一个模块依赖了 5+ 个其他模块
  - 修改一个功能需要同时改 3+ 个文件
- **用户触发**：人发现架构问题，要求 AI 重构

### 重构流程

```
1. 人引导方向（说问题，不说方案）
   "MainPanel 太大了，而且业务逻辑和 UI 混在一起"
          │
          ▼
2. AI 分析问题，输出重构 Spec
   - 当前问题诊断
   - 重构目标
   - 影响范围
   - 分步计划
          │
          ▼
3. 人 review 重构 Spec（确认不会改坏功能）
          │
          ▼
4. AI 执行重构（不改功能，测试必须全过）
          │
          ▼
5. AI 自审查：重构后代码是否达到目标？
```

### 重构原则

- **不改功能**：重构 = 改善内部结构，不改变外部行为
- **小步快跑**：一次只重构一个问题，不要"顺便"
- **测试保护**：重构前确保相关测试通过（如已开启测试）
- **及时提交**：每次重构完成后立即提交，commit message 用 `refactor:`

## 模块 4：AGENTS.md 维护

### 三次原则（硬性约束）

**同一问题/模式出现 ≥ 3 次，才写入 AGENTS.md。**

| 出现次数 | 操作 |
|----------|------|
| 第 1 次 | 在代码审查中提及，不写入 AGENTS.md |
| 第 2 次 | 在代码审查中标记 "Pattern detected: 第 2 次出现"，不写入 |
| 第 3 次 | AI 提议写入 AGENTS.md，**人工确认后**才写入 |

### 为什么？

- 一次教训就上规则 → AGENTS.md 迅速膨胀 → 规则太多 AI 反而忽略
- AGENTS.md 是**提炼后的模式**，不是日志
- 80% 的"问题"其实是偶然，不是模式

### 大小监控

| AGENTS.md 行数 | 状态 | 操作 |
|---------------|------|------|
| 0-200 行 | ✅ 健康 | 正常使用 |
| 200-500 行 | 🟡 关注 | 审查是否有冗余规则 |
| 500+ 行 | 🔴 必须压缩 | 立即触发压缩流程 |

### 压缩策略

当 AGENTS.md 超过 500 行：

1. **分类**：将规则按场景分类（如：前端规则、后端规则、通用规则）
2. **拆分**：拆为 `AGENTS-frontend.md`、`AGENTS-backend.md`、`AGENTS-general.md`
3. **按需加载**：在主 AGENTS.md 中只保留加载规则，按场景引用子文件

```markdown
# AGENTS.md（主文件，保持 <100 行）

## 核心铁律
[来自 SKILL.md 的五条铁律，不可删减]

## 按场景加载
- 写前端代码时：先读 AGENTS-frontend.md
- 写后端代码时：先读 AGENTS-backend.md
- 不确定场景时：读 AGENTS-general.md

## 规范索引
[不写具体规范，只写"XX 类问题 → 见 YY 文件"]
```

4. **去重**：两个规则说同一件事？只保留更清晰的那个
5. **淘汰**：一个规则超过 20 个 Task 没被触发过？删除或归档

### 写入格式规范

```markdown
## [分类]：[简短标题]

> 触发次数：3+ | 最后触发：YYYY-MM-DD | 严重程度：🔴/🟡/🟢

**规则**：[一句话描述]

**为什么**：[一句话说明原因，不写原因 = 删掉这条规则]

**示例**：
❌ 错误做法：[反例]
✅ 正确做法：[正例]
```

### 写入流程

```
AI 发现同一问题第 3 次出现
          │
          ▼
AI 提议："检测到 [问题] 已出现 3 次，建议写入 AGENTS.md：
         [规则内容]
         是否同意？"
          │
          ▼
人确认 → AI 写入 → 检查 AGENTS.md 大小
人拒绝 → 记录原因，重置计数
```

## Harness 反馈闭环

Harness 不是终点——它产生的反馈应该回流到 Spec：

```
Code Review 发现问题
    │
    ├── 是 Spec 遗漏？→ 更新 Spec
    ├── 是模式问题？→ 累计三次 → 写入 AGENTS.md
    └── 是架构问题？→ 触发重构 Spec
```

---

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 审查只检查代码风格，不检查 spec 一致性 | 第一轮审查必须逐条核对验收标准 |
| 发现问题不追溯 spec，只改代码 | 先问"这是 spec 没写好还是代码没写好" |
| 一次重构改太多东西 | 一次只重构一个问题，改完就提交 |
| 第一次遇到问题就加 AGENTS.md 规则 | 三次原则，不破例 |
| AGENTS.md 太大就删内容 | 先压缩（拆分/去重），最后才删除 |
