# CLAUDE.md / AGENTS.md 项目规则体系

## 定位

Spec 定义"做什么"，CLAUDE.md 定义"怎么约束 AI"。它不是一次写完就扔的文档，而是随项目进化的 AI 入职手册。

---

## 环节 0：项目启动——没有就先 /init

```
打开项目
    │
    ▼
项目有 CLAUDE.md 或 AGENTS.md？
    │
    ├── 没有 → /init 自动生成（20 行起步）
    │          人工删减：只保留 AI 读代码读不出来的内容
    │          特殊构建命令、团队 Git 规范、高频踩坑点
    │
    └── 有 → 检查四层优先级
```

**删减标准（每条自问）：** 删掉这条，AI 会不会出错？不会就删。

---

## 四层优先级（加载顺序：先→后，优先级：低→高）

```
组织级规范（强制不可覆盖）
    ｜
用户全局 ~/.claude/CLAUDE.md（个人偏好）
    ｜
项目根 CLAUDE.md（Git 托管，团队共享）★ 主要工作区
    ｜
本地 CLAUDE.local.md（私人配置，不上传，.gitignore）
```

**关键规则：**
- 重要规则必须写入文件——口头指令在 `/compact` 后会丢失
- 多规则文件冲突时，后加载的覆盖先加载的
- 强约束操作用 Hooks，不用文本规则

## 200 行硬上限

| 行数 | 状态 | 操作 |
|------|------|------|
| 0-80 行 | ✅ 理想 | 持续维护 |
| 80-200 行 | 🟡 关注 | 审查是否有可删内容 |
| 200+ 行 | 🔴 必须压缩 | 立即触发拆分/去重/删除 |

**为什么是 200 行？** 50 行遵循率 ~94%，400 行仅 ~71%。篇幅越大，每条规则的效力越低。

---

## 正向指令（避免白熊效应）

不写"不要直接改数据库"，写"数据变更统一走 Service 层"。

| ❌ 否定式 | ✅ 正向指令 |
|-----------|------------|
| 不要跳过 spec 直接写代码 | 代码生成前必须先读对应 spec 文档 |
| 不要用 any 类型 | 所有函数参数和返回值标注具体类型 |
| 不要在组件里直接调 API | 数据获取统一走 hooks，UI 组件只接收 props |
| 不要写巨型函数 | 函数超过 50 行必须拆分 |

**原因：** 否定式指令反向激活被禁止的内容，AI 更容易命中。

## 路径级规则拆分（大型项目）

当规则只对部分目录生效时，拆分到 `.claude/rules/`：

```
.claude/rules/
├── frontend.yml    # 仅 src/ 生效：React 组件规范、状态管理约定
├── backend.yml     # 仅 api/ 生效：Service/Repository 分层、错误处理
└── general.yml     # 全局生效：提交规范、文档引用规则
```

```yaml
# .claude/rules/frontend.yml
paths:
  - src/**/*.tsx
  - src/**/*.ts
rules: |
  - 组件文件一行不超过 120 字符
  - 状态管理用 Zustand，不用 Context 做全局状态
  - UI 组件只接收 props，不直接调 API
```

**收益：** 减少 AI 上下文占用，只加载相关的规则。

## 渐进式披露（按需引用）

AGENTS.md 不塞完整文档，只写索引——"什么场景 → 读哪个文件"：

```markdown
# AGENTS.md（主文件，保持 <100 行）

## 核心铁律
1. Spec → Plan → Task → Code，不可逆
2. 三次原则：同一问题 ≥3 次才写入本文件
3. 测试分层：静态分析 + 单测默认开，E2E 默认关
4. 一个 Task = 一个 Conventional Commit

## 按场景加载
- 写前端代码时：先读 AGENTS-frontend.md
- 写后端代码时：先读 AGENTS-backend.md
- 新功能开发前：先读 docs/specs/ 下对应 spec
- 不确定场景：读 AGENTS-general.md

## 规范索引
- 提交格式 → 见 Conventional Commits 规范
- 测试怎么写 → 见 references/testing-trophy.md
- 重构流程 → 见 references/harness-pillar.md
```

## AI 迭代维护

**三步闭环：**

```
AI 出错被人指出
    │
    ▼
人修正后指令 AI："把这个规则更新到 AGENTS.md"
    │
    ▼
AI 写入 → 检查是否超过 200 行 → 超了就触发压缩
```

**与三次原则的衔接：** 即时修正的规则也要记次数。同一问题被指令修正 ≥3 次 → 正式写入 AGENTS.md 并标注触发次数。

---

## 规则失效排查

1. 确认文件是否正常加载（`/memory` 或检查 `@` 引用）
2. 检查指令是否模糊、无法落地
3. 排查多规则文件间是否有冲突
4. 强约束操作改用 Hooks（如 commit-msg 校验、格式化）
